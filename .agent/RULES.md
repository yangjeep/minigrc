# miniGRC Agent Rules

These rules are binding for non-trivial implementation work unless an explicit, reviewed architecture decision supersedes them.

## 1. Product and architecture invariants

1. **SOC 2 Type II is the primary MVP experience; the core remains framework-neutral.** ISO 27001 must remain usable through shared controls/evidence rather than duplicated framework-specific operational state.
2. **Material compliance state is event-centric.** Immutable domain events are authoritative for facts whose historical occurrence matters. Current state is derived through deterministic projections/read models.
3. **Do not confuse an audit log with event-backed truth.** A mutable row plus a descriptive audit entry is insufficient when the event itself is the compliance fact.
4. **Exactly one relational database backend is active per deployment:** SQLite or PostgreSQL. No dual-write, shadow DB, analytics secondary, cross-DB projection, or mixed runtime mode.
5. **PostgreSQL-specific materialized views are read optimization only.** They must be disposable/rebuildable and never authoritative.
6. **Approved/effective compliance history is immutable.** Changes to approved policies, controls, framework adoptions, or other historical versions create new versions/events rather than rewriting history.
7. **S3-compatible object storage holds bytes; the relational/event model holds compliance meaning.** S3 versioning is infrastructure behavior, not policy/control/evidence business versioning.
8. **External systems are sources, not historical evidence repositories.** Durable evidence needed for an audit is captured/snapshotted with hash and provenance into miniGRC-owned storage.
9. **Connectors produce facts/artifacts, not compliance conclusions.** They never directly mark controls effective, pass tests, close findings, or write projection tables.
10. **AI is advisory/drafting infrastructure, never compliance authority.** It may observe, summarize, prioritize, recommend, nag, and pre-fill, but must not autonomously approve/attest/pass/close/accept risk/fabricate evidence.
11. **One deployment = one organization for MVP.** Do not introduce SaaS-style organization switching or multi-tenant `org_id` plumbing unless a later approved product decision changes this.

## 2. Repository reality beats stale docs

Before implementing, verify the current branch/schema/code. Several historical docs describe earlier constraints that have since changed. Do not preserve a stale restriction simply because an old document still contains it.

If an issue says a dependency exists but merged code does not contain it, treat that as a dependency conflict and surface it.

## 3. Event and projection rules

For material compliance commands:

- validate authorization and domain invariants before append;
- append a stable, schema-versioned event;
- enforce aggregate sequence/idempotency constraints in the selected DB where practical;
- update required canonical projections in the same transaction when immediate consistency is expected;
- make projections deterministic and rebuildable;
- never require a read model/materialized view to reconstruct authoritative history;
- distinguish `occurred_at` from `recorded_at` when backdating/import semantics matter;
- never forge historical human actions during migration. Migration/import/bootstrap facts must be identified as such.

Do not event-source UI sort order, transient connection-test state, theme preferences, or other noise unless a concrete compliance reason exists.

## 4. Data and migration rules

- Schema changes go through Alembic.
- Migrations must work on both supported database engines unless the issue explicitly introduces a backend-specific read optimization with an equivalent fallback.
- Review autogenerated migrations manually.
- Do not destructively rewrite historical approved/effective state.
- Backfills must use deterministic, documented matching rules and fail safely on ambiguity.
- A migration must not invent historical actions that cannot be supported by existing data.
- Exactly one DB backend must be selected unambiguously at startup/configuration time.
- If SQLite -> PostgreSQL migration is added later, it is an explicit offline/admin cutover, not runtime coexistence.

## 5. Authorization and identity

- Authentication and application authorization are separate concerns.
- Preserve local break-glass administration while OIDC is optional/being introduced.
- Generic OIDC must use issuer + subject as external identity authority; do not silently merge accounts solely by email.
- External group/claim values grant only explicitly configured application roles; unknown values fail least-privilege.
- Material authorization changes should be auditable/event-backed where the product needs historical reconstruction.
- Never let AI or connector output bypass normal authorization/validation commands.

## 6. Secrets and external integrations

Never commit or persist secrets in:

- domain events;
- audit-package exports;
- logs;
- worklogs;
- fixtures/snapshots;
- connector result payloads;
- AI prompts retained for audit;
- client-visible responses after configuration.

Use repository-approved encrypted/secret mechanisms. Do not log raw OAuth tokens, API keys, database passwords, client secrets, or provider credentials.

Treat configurable external URLs/endpoints as SSRF/security boundaries.

## 7. Evidence integrity

Evidence capture should retain the minimum useful provenance, such as:

- source/provider;
- stable source object identifier;
- source revision/version when available;
- source modified timestamp where useful;
- capture timestamp;
- content hash;
- MIME/type/size;
- connector execution or actor correlation.

Changing or deleting the provider source later must not mutate prior captured evidence.

Evidence is evidence, not a test result or effectiveness conclusion.

## 8. Connector rules

Connector manifests/contracts declare capabilities and required permissions/scopes.

Runtime rules:

- validate connector compatibility and output contract before ingestion;
- reject undeclared capabilities/results;
- keep connector config/runtime health separate from compliance truth;
- ingest material outputs only through authorized core commands/events;
- retries must not duplicate captured facts/artifacts silently;
- connector removal/disable must not delete historical captured evidence;
- core must remain functional with connectors disabled/unavailable.

## 9. AI / Digital Compliance TPM rules

The deterministic application decides whether a readiness condition exists and who is eligible for action. AI may phrase, summarize, prioritize, or draft around that condition.

Generated text must:

- be visibly draft/AI-assisted where user-facing;
- ground itself in authorized miniGRC facts;
- expose missing information instead of hallucinating it;
- preserve source references/context where practical;
- require the same authorized application command/form as human-authored text before changing material state.

Do not persist hidden chain-of-thought.

## 10. Testing expectations

Every changed core use case needs automated coverage for relevant dimensions:

- success path;
- authorization/role boundaries;
- invalid input;
- retry/idempotency/replay where applicable;
- historical immutability;
- migration/backfill safety;
- SQLite/PostgreSQL equivalence for backend-neutral behavior;
- secret leakage and external failure handling for integrations;
- deterministic projection rebuild for event-backed state.

Run repository-standard tests/lint/format and relevant security/dependency checks before declaring completion.

## 11. Git and scope discipline

- Keep diffs focused on the issue.
- Do not refactor unrelated code because it is nearby.
- Commit in small logical increments using the repository convention (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`).
- Push the task branch and create/update a draft PR unless the task explicitly says otherwise.
- Do not merge without explicit authorization.
- Do not delete meaningful tests to make CI green.

## 12. Stop conditions

Stop and report rather than choosing silently when:

- product/architecture invariants materially conflict;
- a required dependency is not actually merged;
- a destructive migration/backfill cannot be proven safe;
- historical compliance truth would need to be invented or rewritten;
- security/authorization semantics are materially ambiguous;
- an unapproved new infrastructure/service is required;
- correct implementation requires materially expanding MVP scope.

Do not stop for ordinary implementation decisions that current repository patterns can resolve.
