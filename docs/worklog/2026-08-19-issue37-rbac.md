# Issue #37: RBAC (admin/operator/reader/auditor)

**Date:** 2026-08-19
**Author:** Claude (agent)
**Type:** feature

## Summary

Widens `User.role` from a binary `("user", "admin")` distinction to four
roles: `admin`, `operator`, `reader`, `auditor`. See
`docs/superpowers/specs/2026-08-19-issue37-rbac-design.md` for the full
design, repository-reality inventory, and the two pieces of the issue's
own scope explicitly deferred (configurable OIDC claim/group→role
mapping, needs #16-#20; scoped service/API principal model, needs
#36/#23-#28) because their real prerequisites are not merged.

A new `require_write_access` dependency (`admin`/`operator` only) now
gates every mutation route that was previously reachable by any
logged-in user regardless of role — closing a real gap where
`reader`/`auditor` (and, before this issue, any `user`) could perform
material compliance mutations through routes that were only
`require_login`-gated.

## What changed

- `app/models.py` — `USER_ROLES = ("admin", "operator", "reader",
  "auditor")`; `role` column default `"user"` → `"operator"`.
- `app/deps.py` — new `require_write_access` (`WRITE_ROLES =
  frozenset({"admin", "operator"})`).
- `app/registers/router.py::_check_permission` — `create`/`edit`/`delete`
  now unconditionally require a write role, in addition to any stricter
  `require_admin_for` override a register already declares. Closes a
  real gap: the `controls` and `framework-requirements` registers had no
  `require_admin_for` at all, so `create`/`edit`/`delete` on them were
  reachable by any logged-in user.
- Every plain-route mutation inventoried in the design doc's §1 switches
  `Depends(require_login)` → `Depends(require_write_access)`:
  `controls.py` (`set_control_owner`, `generate_control_occurrences`,
  `create_control_occurrence`, `add_mapping`), `occurrences.py`
  (`perform`), `evidence.py` (`map_requirement`, `map_control`),
  `people.py` (`create_person`, `update_person`), `policies.py`
  (`create_policy`, `update_policy`, `upload_policy_version`,
  `retire_policy`), `risks.py` (`create_risk`, `import_risks`),
  `frameworks.py` (`create_framework`, `update_framework`,
  `create_requirement`, `import_requirements`, `update_assessment`,
  `add_note`), `vendor_systems.py` (create/edit vendor,
  `create_roster_snapshot`).
- `app/routers/google_oidc.py` — auto-provisioned non-first sign-in now
  gets `operator` (was `user`); first auto-provisioned user still gets
  `admin`, unchanged.
- `app/routers/admin_users.py::create_user`, `app/cli.py::create_user` —
  both hardcoded `role="user"`; fixed to `role="operator"` (see Bugs
  found below — these would have violated the new CHECK constraint).
- Migration `96edf74d9219_expand_user_roles_for_rbac.py`: drop
  `ck_user_role` → `UPDATE users SET role='operator' WHERE role='user'`
  → recreate `ck_user_role` with the widened role set. Deterministic,
  additive-only; no existing account gains or loses privilege. Downgrade
  path is symmetric with a documented data-loss-risk caveat for any
  `reader`/`auditor` rows created after the upgrade.

## Bugs found during verification

1. **`User.role`'s ORM-level column default was still `"user"`**
   (`app/models.py`) — any code constructing `User(...)` without an
   explicit role (e.g. the `test_user` fixture, and any future signup
   path relying on the default) would have inserted a value the new
   `ck_user_role` constraint rejects, failing at flush/commit with an
   `IntegrityError`. Root cause: the rename was applied to `USER_ROLES`
   and route dependencies but missed the model's own default. Fixed by
   changing the default to `"operator"`. No regression test needed
   beyond the existing suite — every fixture/test that relies on this
   default (`tests/conftest.py::test_user`, `tests/test_admin_users.py`,
   etc.) now exercises it directly and would fail loudly if it regressed.
2. **`admin_users.py::create_user` and `cli.py::create_user` both
   hardcoded `role="user"`** for newly created accounts — same failure
   mode as #1, found by the same grep sweep. Fixed to `"operator"`.
   Regression coverage: `tests/test_admin_users.py::test_create_user_via_admin`
   now asserts `role == "operator"`; `tests/test_admin.py::test_first_created_user_becomes_admin`
   asserts the second CLI-created user gets `"operator"`.

Both were caught by grepping for every `role="user"`/`role == "user"`
literal across `app/` before running the suite, not by a failing test —
worth calling out since they would otherwise have been a first-real-use
production `IntegrityError` (every new local/admin-created/CLI-created
account) despite the targeted RBAC tests passing.

## Known deferred/untested paths

- Configurable OIDC claim/group→role mapping — out of scope until
  #16-#20 (generic OIDC) lands; see design doc §6.
- Scoped service/API principal model for non-human access (#36,
  #23-#28 connectors) — out of scope until those land; see design doc
  §7. `USER_ROLES` is committed to staying a closed set of the four
  human roles above.
- `reader` vs. `auditor` are identical in server-side access this
  slice — no object/period-scoping mechanism exists yet (#30) to
  express the audit-scope distinction the product eventually wants
  between them. Defining the coarse role now and staging the scoping
  filter once #30 exists is the design doc's explicit, issue-sanctioned
  sequencing decision, not an oversight.
- PostgreSQL migration/role tests are gated on `TEST_DATABASE_URL` and
  were not run against a live PostgreSQL server in this sandbox (no
  local instance available); they will run in CI's `test-postgres` job.
